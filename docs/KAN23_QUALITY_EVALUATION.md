# KAN-23 quality evaluation, first pass

6 October 2026. `fixtures/kan23_typed_cases.json` has 30 labeled synthetic cases for date, budget, and enum comparisons, including tentative and negated facts, entity and predicate mismatches, a leap day, a year boundary, missing evidence, and an inactive decision. Each case labels the expected classification, whether a finding should exist, and the expected baseline/update character spans when it should. `tests/test_quality_eval.py` builds typed inputs from those labels and checks the assessment output and snapshot-resolving quote locations.

The domain run passed all 30 classifications: 5 contradictions, 7 supports, 14 uncertain, and 4 unassessed. It produced 5 expected alerts and no unexpected alerts, giving 100% alert precision and recall **within this synthetic set**. All 12 emitted findings kept quotes contained in their synthetic source text. The test finished in 0.007 seconds on this machine; that is domain execution time, not API or browser latency.

Three Firestore emulator integration checks also passed. A source changing to `access_required` removed its fact from the next assessment and left coverage unassessed. A content change without a matching extraction hash also removed the stale fact. Replaying the same assessment request kept one alert and the same run receipt. These checks cover the assessment store; they do not prove native Drive permission checks or duplicate prevention during folder refresh.

I reran all three checks on 9 October against the local Cloud Firestore emulator at `127.0.0.1:8089`; all passed in 0.471 seconds. This remains an emulator result, with no live database writes.

On 8 October, an isolated synthetic project (`proj_kan23_latency_20261008`) was assessed by clicking **Run assessment** in the running Reviews page. The request went through the local API, the real Cloud Tasks queue, the private Cloud Run worker, and the named `decision-radar` Firestore database. The browser changed from queued to completed and displayed two findings and one alert. The saved job had one attempt; its Firestore timestamps were 02:23:44.474177 to 02:24:09.691070 UTC, about 25.2 seconds. The browser showed the completed result at roughly 30 seconds from the click. This is one observation with a synthetic Auth emulator user and previously saved evidence, not a fresh Drive or Gemini run. It does not establish a latency distribution or review time.

The KAN-26 live rehearsal on 8 October exposed a repeatability case for this gate. In synthetic project `proj_oauth_pr10_uat_20261007`, the same `vendor-update.txt` sentence, “Acme Logistics delivery date is October 24, 2026.”, had produced one verified `acme_logistics` / `delivery_date` fact. A fresh Vertex Gemini extraction with the same trusted wording returned a different entity/predicate interpretation and zero verified facts. The subsequent Cloud Tasks assessment completed with zero alerts and three unclear assumptions, although the prior alert remained in history. Retrying extraction on the same snapshot produced one verified fact; reassessment restored the cited nine-day alert and left the two unrelated assumptions unclear. This is a real model-output variance, not a measured false-positive or false-negative rate.

PR #20 merged on 9 October. It reuses a previously verified extraction when the source snapshot, monitored assumption, alias wording, and saved fact still match; uncertain results and changed inputs run Gemini again. The deployed Sources control reused the October 24 verified fact, and assessment retained the cited nine-day alert. This addresses the unchanged-input demo regression. It does not measure how often Gemini varies on fresh or changed evidence, so that remains a KAN-23 evaluation case.

A citation-span regression check now uses the same exact quote in two different source snapshots. It verifies the labeled offsets (10–41 and 28–59) and a different span ID for each snapshot. Both this check and the 30 typed classification cases passed. This supports snapshot-bound citations, but it does not establish that native Drive source links stay accessible after permission changes.

The date rule is day-only. A timestamp candidate with an explicit `+14:00` offset is rejected instead of being silently cast to 24 October, which could mean a different UTC day. This regression check passed. Timezone normalization remains a documented exception for timestamp-bearing sources; the MVP needs an explicit source timezone or human-confirmed calendar date before such evidence can drive an alert.

This is an initial gate, not KAN-23 completion. The set has only five positive alerts and does not yet exercise native Drive permission loss, duplicate ingestion across refreshes, timestamp normalization, fresh-extraction variance, or measured human review time. The citation-span and timestamp checks are local rather than browser measurements. Those remaining cases need integration checks and a fresh Drive-to-review browser pass before this PR can be merged or the ticket marked done.

## 16 October live-source browser pass

In the synthetic `proj_kan15_connection_uat_20261015` project, a fresh Drive folder refresh completed under the separated Cloud Run worker identity and yielded 11 native sources. The local branch UI and API used real Vertex, named Firestore, Cloud Tasks, and the deployed standard worker. The first Google Doc extraction failed because Gemini returned the same decision quote with paragraph line breaks collapsed to spaces. The citation resolver now accepts that whitespace-only variation only when it identifies one source span, then saves the exact source characters; altered or ambiguous quotes remain invalid. Retrying **Extract with Gemini** in the browser saved the Doc suggestion. Extracting the native `vendor-update.txt` saved one verified October 24 delivery-date fact.

The browser's **Run assessment** action completed through Cloud Tasks and the private worker. Reviews showed one assessed, medium contradiction with the original October 15 assumption and new October 24 fact, each linked to its exact source citation. The impact graph showed the direct +9 day challenge and no downstream decision, which matches this test project's data. I submitted **Request clarification** with a synthetic rationale; after reloading the page, the audit entry remained and the decision stayed at revision 1. Browser captures are `/tmp/decision-radar-kan23-real-extraction-20261016.png` and `/tmp/decision-radar-kan23-impact-review-20261016.png` on the test machine.

This pass closes the fresh Drive-to-review integration gap for this test case. The broader KAN-23 gates listed above remain open, especially native permission loss, duplicate refresh, timestamp policy, fresh-extraction variance, and measured human review time.

I also repeated **Refresh folder** in the deployed web app against the same native Drive folder, then clicked **Run assessment** in the branch app. Both returned completed. A read-only check of the named Firestore database found 11 source records, one immutable version each for the decision Doc and vendor text file, one assessment run, one request, and one alert. Their current version IDs matched the first crawl. The review page still showed one assessed alert. This verifies unchanged-input refresh and assessment replay for this live test folder; it does not cover changed files or simultaneous refresh submissions. The local branch API's refresh action returned 503 because its local Google Drive configuration is absent, so the repeat refresh used the deployed staging API.

A second synthetic **Request clarification** pass timed from choosing the action through the visible saved audit entry took at most 15.7 seconds in the agent-controlled browser; the entry was persisted without a decision revision change. This includes tool round trips and polling delay, so it is an upper bound for this automated pass, not a measured human review-time distribution. The user-facing review-time target still needs human sampling or an explicitly accepted exception.
